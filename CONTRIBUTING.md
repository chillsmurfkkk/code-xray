# Як працюємо над Code Xray

Кожен відповідає за код, перевірки та документацію свого модуля. Спільні
правила зберігаються в репозиторії, щоб локальні копії інструкцій не розходилися.

Власник каталогу погоджує зміни, а авторство для лабораторної підтверджується
фактичною реалізацією. Початкові контракти E0 і подальші алгоритми можуть мати
різних авторів.

## Робочий цикл

1. **Перевірюваний результат.** Задача має автора, очікувану поведінку й критерії
   приймання. Окрема гілка починається від актуального `main`, наприклад
   `c/read-commit-tree`; великий модуль розбивається на завершувані частини.
2. **Код разом із доказом.** Автор додає доречні перевірки й записує команду,
   вхід та результат. Для помилкового, неповного або скасованого входу
   перевіряється окремий стан. Для редагування тексту достатньо перевірити
   посилання й твердження, нові програмні тести не потрібні.
3. **Спільні контракти.** Зміна типу чи семантики погоджується зі споживачами;
   код, фікстури й опис змінюються разом. `TSNode`, libgit2-вказівники
   й віджети не передаються між модулями як API.
4. **Чужий перегляд.** Звичайний шлях у `main` — PR зі збіркою, перевірками та
   схваленням іншого учасника. A переглядає B/C, C — A/D; зміни контрактів
   також дивляться споживачі. Rebase and merge зберігає авторів окремих комітів.

Повний Windows-сценарій із кореня репозиторію:

```powershell
cmake --preset windows-x64
cmake --build --preset windows-x64
ctest --preset windows-x64
```

Залежності й налаштування — в [E0](docs/e0-kickoff.md). `contracts-only`
виключає парсер, Qt, JSON-профілі/рушій та реальний експорт, тому не замінює
повну перевірку. Для sandbox із недоступною системною тимчасовою папкою є
[сценарій TEMP/TMP у build](docs/lab1-verification.md).

## Який документ оновлювати

| Зміна | Документація разом із кодом |
|---|---|
| Збірка, запуск, залежності або доступні можливості | README і відповідний технічний опис. |
| Публічний контракт або правила обчислення | API, фікстури/приклади, технічний опис; README для загальних домовленостей. |
| Особистий внесок до лабораторної | `docs/contributions/<A–D>.md` і підсумок `docs/contributions.md`, якщо змінюються числа/готовність. |
| Підготовка або оновлення здачі ЛР №1 | `docs/lab1-<A–D>.md`, конкретний SHA й результати перевірки. |
| Досвід інтеграції бібліотеки | Особиста `docs/retrospectives/<GitHub-login>.md`; її автор пише сам. |

Повний звіт готується до здачі на зафіксованому знімку. Після робочого PR
достатньо актуальних рядків внеску й технічного опису; весь звіт щоразу
переписувати не потрібно.

## Єдине оформлення

Особистий реєстр містить дату/SHA, числа, походження коду, окремі рядки
типів/полів/нетривіальних реалізацій, ієрархії, клієнти поліморфізму та межі
доказів. Сталі ID й фактичні символи важливіші за дослівний збіг із планом.
Правила підрахунку й статусів — у [спільному реєстрі](docs/contributions.md).

Звіт ЛР №1 має спільну послідовність: мета й власна частина; відповідність
вимогам; інкапсуляція; ієрархії та три поліморфні клієнти; демонстрація й
результати; висновок і незавершені частини. Повні переліки залишаються в
реєстрі, щоб їх не підтримували двічі. Часткова реалізація описується прямо.

Markdown ведемо українською, назви API та повідомлення програми зберігаємо
без перекладу. Посилання на файли відносні в межах репозиторію; SHA фіксує
предмет захисту незалежно від подальших змін `main`. Не включаємо локальні
абсолютні шляхи, вигадані запуски й приписаний іншому автору особистий досвід.
Вихідні матеріали курсу та локальні персональні гайди не копіюємо в продукт.
