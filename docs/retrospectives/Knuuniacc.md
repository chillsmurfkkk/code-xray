## 1. Контекст задачі та вибір бібліотеки

У проєкті Code Xray завдання розробника D полягає у проведенні структурно-семантичного порівняння двох знімків коду (`ComparisonReport`), побудові аналітичних трендів за ланцюжком комітів (`TrendReport`) та експорті результатів аудиту у відкриті формати — структурований JSON для машинного аналізу та стилізований HTML-звіт для розробників і керівників проєктів.

Для генерації HTML-звітів було обрано бібліотеку **Inja** (у поєднанні з **nlohmann/json**) з таких причин:
- **Jinja2-подібний синтаксис**: Підтримка декларативних конструкцій — циклів (`## for item in rows`), розгалужень (`## if item.has_findings`), фільтрів та змінних (`{{ entityKey }}`) прямо в розмітці шаблону без необхідності захаращувати C++ код ручною конкатенацією рядків або складною логікою форматування.
- **Природна інтеграція з `nlohmann/json`**: Inja безпосередньо приймає об'єкти `nlohmann::json` як контекст даних (data model), що забезпечує єдиний конвеєр серіалізації: C++ структури ядра → JSON-модель даних → рендеринг у HTML або прямий запис у `.json`.
- **Header-only архітектура**: Легка інтеграція в систему збірки CMake через менеджер пакетів `vcpkg`, відсутність важких динамічних бібліотек чи інтерпретаторів часу виконання.
- **Безпека та ізоляція**: Можливість відокремити візуальне подання від аналітичного ядра, що дозволило реалізувати безпечний рендеринг без ризику падіння застосунку.

## 2. Архітектура та реалізовані можливості

Інтеграція Inja зосереджена в [`src/review/exporter.cpp`](../../src/review/exporter.cpp) та прихованій за інтерфейсом [`ReportExporter`](../../src/review/exporter.hpp) ієрархії:

1. **Моделювання даних (`buildReportModel`)**:
   - Перетворення типізованих структур ядра (`ComparisonReport`, `ReviewItem`, `Coverage`, `MetricDelta`, `FindingChange`) на проміжну модель `ReportModel`.
   - Формування людино-читабельних описів: людські назви правил (`long_function`, `deep_nesting`), перетворення числових дельт метрик у компактний вигляд (`+5`, `-2`), фіксація станів порушень (нове, усунене, наявне, видалене з кодом).
   - Серіалізація підсумку: загальна кількість змін, додані/видалені функції, діагностика повноти знімка (`Coverage`).

2. **Захист від HTML-ін'єкцій (`escapeHtmlText`)**:
   - Оскільки сигнатури функцій C++ містять кутові дужки шаблонів (`std::vector<int>`), амперсанди посилань (`&`) та лапки, реалізовано попередню санітизацію тексту для запобігання пошкодженню верстки HTML або потенційним вразливостям відображення.

3. **Вбудований дизайн Gruvbox**:
   - Шаблон HTML містить повноцінні CSS-стилі у палітрі Gruvbox (Dark/Light), адаптивну таблицю з підсвічуванням статусів змін (зелений для доданого, червоний для видаленого, жовтий для модифікованого), бейджі повноти та метадані аналізу. Згенерований HTML є повністю автономним (standalone) і не потребує завантаження зовнішніх шрифтів чи CDN.

4. **Атомарний безпечний запис (`writeReportSafely`)**:
   - Запис нового звіту спочатку відбувається у тимчасовий файл поруч із цільовим (`.tmp.<pid>.<random>`).
   - Якщо цільовий файл існує, перевіряється прапорець `overwriteConfirmed`. При підтвердженні створюється страхувальна резервна копія (`.bak`), після чого виконується атомарна заміна (`std::filesystem::rename`).
   - У разі помилки чи скасування всі тимчасові файли гарантовано видаляються, а попередній файл користувача залишається неушкодженим.

5. **Єдина серіалізація для прев'ю та експорту**:
   - Метод `renderReport()` використовує той самий конвеєр Inja, що й фізичний запис у файл. Завдяки цьому попередній перегляд в UI (`ExportPage`) на 100% збігається з фактично збереженим файлом на диску.

## 3. Складнощі, виклики та уроки

1. **Кооперативне скасування та потокобезпечність (F11/T12)**:
   - Формування великих звітів та рендеринг Inja для тисяч сутностей може займати помітний час. Тому операції прев'ю та експорту були винесені у фоновий `QThread` з підтримкою `std::stop_token`.
   - Складним моментом виявилася синхронізація станів при пізньому скасуванні: якщо атомарний запис на диск уже завершився (`rename`), операція вважається успішною, і користувач обов'язково отримує квитанцію `ExportReceipt`, навіть якщо сигнал скасування прийшов за мілісекунду до оновлення GUI.

2. **Утилізація ресурсів і розділення життєвого циклу задач**:
   - Під час рев'ю було виявлено, що створення фонових потоків без очищення призводило до накопичення об'єктів `QThread`. Проблему вирішено прив'язкою `deleteLater` до сигналу `finished` та централізованим методом `cleanupWorkerThread()`.
   - Заміна звіту на сторінці під час генерації старого прев'ю тепер коректно інвалідує попередній `previewJobId_`, відкидаючи застарілі дані, тоді як окремий `exportJobId_` гарантує збереження квитанції про успішний запис файлу.

3. **Синтаксичні тонкощі шаблонізатора**:
   - Inja чутлива до пробілів усередині керуючих інструкцій та вимагає чіткої структури блоків `## for` / `## endfor`. Зручним виявилося попереднє винесення всієї логіки обчислення дельт у C++, залишаючи в шаблоні виключно пряме відображення вже підготовлених текстових полів.
